# E0000-02 Handoff

Result: passed for the approved reversible remediation

Owner decision: D-E0000-002, Gate B approved 2026-08-29.

## Metadata findings

- Before remediation, Git tracked `.proof/config.json`,
  `.proof/keypair.json`, and `.proof/storage/storage.db`.
- The directories were mode `0755`; the three files were mode `0644`.
- Path-only history inspection found `.proof` in commits `94c20b8` and
  `035a607`. Untracking the current revision does not remove those copies.
- `.gitignore` already contains `.proof/`; no ignore-rule edit was required.

No private-key or database contents were read, printed, hashed, decoded,
copied, archived, or uploaded. A content scan was intentionally not performed:
the tracked private-key path itself establishes exposure and the task prohibits
reading its contents.

## Actions taken

- Set `.proof` and `.proof/storage` to mode `0700`.
- Set the three known runtime files to mode `0600`.
- Removed the three paths from Git tracking with exact `git rm --cached`
  targets. The working-tree files remain present and ignored.
- Did not delete files, rotate identity, rewrite history, contact external
  parties, or modify runtime data.

## Verification

- `rtk stat -c '%a %n' ...` — known directories are `700`; files are `600`.
- `rtk git ls-files .proof` — no tracked paths returned.
- `rtk git check-ignore -v ...` — all three paths match `.gitignore:2`.
- `rtk git diff --cached --name-status -- .proof` — exactly three tracking
  deletions; local preservation was separately verified with `stat`.

## Rotation impact

The existing rotation command archives the old private key, generates a new
principal, changes `config.json`, and adds the new principal to SQLite. It does
not create a signed old-to-new identity link, revoke the old identity, migrate
identity-bound delegations or pending approvals, or change existing proofs.
Proof envelopes currently have no rotation/expiry link. Storage-level
verification can retain old public principals, but the current CLI `verify`
path requires the proof actor to match the current workspace keypair and would
reject prior-actor proofs after rotation.

Therefore rotation was not performed in this task. A follow-up security
migration must define identity succession/revocation, old-proof verification,
delegation and in-flight-run handling, recovery, and rollback before rotating.

## Residual risk

The key must still be treated as compromised because historical Git objects
retain it and existing clones may contain it. Current untracking prevents new
snapshots but is not revocation. History rewriting, coordinated rotation, and
any notification remain separately owner-gated.
