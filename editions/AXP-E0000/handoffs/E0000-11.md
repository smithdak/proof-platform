## Compatibility and residual requests

- The HTTP JSON success envelope is unchanged. Successful HTTP executions now
  persist the engine-created context/proof through the already configured store,
  which is required for exact replay and aligns behavior with the documented
  evidence path.
- HTTP/WS currently use `.proof/data/proofs/proofs.sqlite3`, while CLI/MCP use
  `.proof/storage/storage.db`. Unifying those paths requires the separately
  gated compatibility and migration decision explicitly excluded from E0000.
- Within each `AppState`, the engine and request contexts now share one signing
  identity. HTTP still generates that identity when constructing state; a
  future requirement to load `.proof/keypair.json` persistently should use a
  shared, security-reviewed workspace identity loader rather than duplicating
  private-key parsing in this transport.
