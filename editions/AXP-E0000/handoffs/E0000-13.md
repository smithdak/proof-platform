# E0000-13 Handoff — Shared exact-replay design

Result: design complete; E0000-14 is blocked on the owner Gate B decision below

Dispatch note: after design review, the orchestrator split the implementation
boundary into three disjoint W4 packets: E0000-14 owns kernel API/engine,
E0000-16 owns SQLite migration/storage, and E0000-15 owns HTTP/WebSocket error
mapping. References below to the combined E0000-14 implementation map to those
three packets without changing the proposed interface or Gate B boundary.

## Boundaries and current gap

- This was a read-only design pass over the frozen contracts, architecture,
  engine/store APIs, approval replay, SQLite migrations/tests, and transport
  error mappings. Only this handoff changed. `.proof` and the Git index were
  not read or touched; no code, contract, registry, schema, migration, or test
  was changed or run.
- `OperationHandler::execute` returns only JSON. The engine creates and stores
  the proof after the handler has already mutated state, and `ExecutionStore`
  has no idempotency-key lookup or atomic output/proof completion operation.
  Handler-local replay therefore cannot return the original signed proof or
  prevent two callers from entering the mutation.
- Approval replay is a useful insert-once precedent, but its request ID is not
  the frozen `(operation, version, idempotency_key)` tuple and it does not claim
  a key before mutation. A separate shared execution replay record is required.
- Existing registry rows broadly say `required-uuidv7` even though many current
  input schemas do not contain `idempotency_key`. Activating exact replay for
  every such row in E0000 would be a breaking expansion. The two frozen target
  handlers must opt in explicitly; existing handlers retain legacy behavior.

## Proposed kernel API

Add these public, root-re-exported types in `proof-kernel`:

```rust
pub enum IdempotencyPolicy {
    None,
    RequiredUuidV7ExactReplay,
}

pub struct ExecutionReplayKey {
    pub operation: String,
    pub version: String,
    pub idempotency_key: Uuid,
}

pub struct ExecutionReplayClaim {
    pub key: ExecutionReplayKey,
    pub input_digest: ContentDigest,
    pub claim_token: Uuid,
    pub claimed_by: PrincipalId,
    pub claimed_at: DateTime<Utc>,
}

pub enum ExecutionReplayClaimResult {
    Acquired,
    Completed(ExecutionOutcome),
    Conflict,
    InProgress,
    Failed,
    Unsupported,
}
```

`OperationHandler` gains a default method returning
`IdempotencyPolicy::None`. E0000-06 overrides it with
`RequiredUuidV7ExactReplay` only for `edition.create::v1` and
`changeset.commit::v1`. The default preserves source compatibility for all
current handler implementations and avoids changing `RegistryEntry` or
`ExecutionContext`.

`ExecutionStore` gains three object-safe methods. The default claim returns
`Unsupported`, while default completion/failure methods return an
unsupported-store error, so existing external implementors still compile:

```rust
fn claim_execution_replay(
    &self,
    claim: &ExecutionReplayClaim,
) -> Result<ExecutionReplayClaimResult, String>;

fn complete_execution_replay(
    &self,
    claim: &ExecutionReplayClaim,
    context: &ExecutionContext,
    outcome: &ExecutionOutcome,
) -> Result<(), String>;

fn fail_execution_replay(
    &self,
    claim: &ExecutionReplayClaim,
    failed_at: DateTime<Utc>,
    failure: &str,
) -> Result<(), String>;
```

`SqliteStore` and the kernel `RecordingStore` implement all three. No new
engine entry point is needed: all four existing execution methods continue
through `execute_operation`, so evidenced, value-only, and approval-authorized
calls cannot bypass the replay policy.

For an opted-in handler, the engine requires a top-level string
`idempotency_key`, parses it as UUID version 7, canonicalizes the complete input
including that field, and computes the existing domain-separated
`ArtifactKind::OperationInput` BLAKE3 digest. Exactness is canonical JSON
equivalence, not caller byte order. An opted-in call without durable compatible
storage fails before handler entry; an in-memory unpersisted fallback is not
allowed.

## Lifecycle and atomicity

The sequence is fixed:

1. Resolve the registry entry; verify current governance/approval, lifecycle,
   and delegation; resolve the handler and its replay policy. Unauthorized
   callers cannot probe or reserve replay keys.
2. Validate the required UUIDv7 key and canonicalize/digest the complete input.
   With durable storage absent, stop before mutation.
3. Call `claim_execution_replay` before the benchmark gate and before handler
   entry. SQLite uses `BEGIN IMMEDIATE` and the tuple primary key.
4. Interpret the claim result:
   - `Acquired`: this caller alone may continue.
   - `Completed`: structurally verify the stored proof operation and input and
     output digests, then return the stored `output` and the same proof ID,
     body, and signature. Do not invoke the handler or mint new evidence.
   - `Conflict`: same tuple, different canonical input; return conflict before
     handler entry.
   - `InProgress`: return a retryable busy conflict; never wait while holding a
     SQLite transaction and never enter the handler. A claim that persists
     instead of completing requires operator reconciliation.
   - `Failed`: return an indeterminate failure requiring reconciliation; never
     enter the handler.
   - `Unsupported`: return storage-required before handler entry.
5. Only an acquired claimant evaluates execution-only gates and invokes the
   handler. On any benchmark, handler, or evidence error, best-effort transition
   the claim to `failed`; if recording the failure itself fails, return storage
   failure. Neither state is a completed replay record.
6. Create the proof once. `complete_execution_replay` validates the claim token,
   state, tuple, input digest, proof operation, actor/delegation/timestamp, and
   proof output digest. One SQLite transaction inserts the execution context,
   inserts the immutable proof, and changes the row from `claimed` to
   `completed` with canonical output and the serialized original proof. A
   completion error returns no success response and leaves the key blocked.
   Retrying the identical completion is idempotent; a different completion is
   a storage conflict.

The domain mutation cannot be in the same SQLite transaction because the
public handler boundary does not expose a shared transaction and domain stores
may not be SQLite. The safe residual crash window is therefore deliberate:
after claim and before completion, process death may leave an already-applied
mutation with a `claimed` row. Claims have no expiry, lease stealing, deletion,
or automatic retry in E0000. On restart, `claimed` and `failed` both fail closed.
An operator/domain-specific reconciler must establish whether the mutation
occurred; until such a later gated recovery API exists, the caller uses a new
UUIDv7 key only after reconciliation. This preserves at-most-once mutation and
never falsely invents an original output/proof.

Concurrent callers on one or multiple SQLite connections cannot both acquire:
the first immediate transaction inserts the tuple, while every loser observes
`claimed`, `completed`, or an input conflict after the winner commits. A loser
may retry after completion to obtain the original outcome.

## Migration 11

Append, never edit, migration **11**, description
`create exact execution replay ledger`:

```sql
CREATE TABLE execution_replays (
    operation TEXT NOT NULL,
    version TEXT NOT NULL,
    idempotency_key TEXT NOT NULL,
    input_digest TEXT NOT NULL CHECK (length(input_digest) = 64),
    state TEXT NOT NULL CHECK (state IN ('claimed', 'completed', 'failed')),
    claim_token TEXT NOT NULL UNIQUE,
    claimed_by TEXT NOT NULL,
    claimed_at TEXT NOT NULL,
    completed_at TEXT,
    failed_at TEXT,
    failure TEXT,
    output_json TEXT,
    proof_id TEXT UNIQUE REFERENCES proofs(id),
    proof_json TEXT,
    execution_context_id TEXT UNIQUE REFERENCES execution_contexts(id),
    PRIMARY KEY (operation, version, idempotency_key),
    CHECK (
        (state = 'claimed'
         AND completed_at IS NULL AND failed_at IS NULL AND failure IS NULL
         AND output_json IS NULL AND proof_id IS NULL AND proof_json IS NULL
         AND execution_context_id IS NULL)
        OR
        (state = 'completed'
         AND completed_at IS NOT NULL AND failed_at IS NULL AND failure IS NULL
         AND output_json IS NOT NULL AND proof_id IS NOT NULL
         AND proof_json IS NOT NULL AND execution_context_id IS NOT NULL)
        OR
        (state = 'failed'
         AND completed_at IS NULL AND failed_at IS NOT NULL
         AND failure IS NOT NULL AND length(failure) > 0
         AND output_json IS NULL AND proof_id IS NULL AND proof_json IS NULL
         AND execution_context_id IS NULL)
    )
);

CREATE INDEX idx_execution_replays_state_claimed_at
    ON execution_replays(state, claimed_at);
```

UUIDv7 shape and digest correctness remain application validations; SQLite
cannot reliably express UUID version validation. `proof_json` intentionally
duplicates the referenced audit proof, following `approval_executions`, so the
exact replay envelope cannot drift if another proof query policy changes. The
completion transaction requires the duplicated proof to equal the inserted
proof. Unique proof and context references prevent either audit artifact from
being attached to more than one idempotency tuple; a separate approval replay
row may still reference the same proof JSON.

Upgrade from v10 creates an empty ledger; historical mutations are not
backfilled because their original output and signed proof cannot be inferred.
The down migration drops the index and table only. Schema rollback is
reversible, but operational rollback is not safe while opted-in mutations are
available: quiesce writers, preserve/export the ledger, roll back application
policy so the two operations fail closed, then roll back to v10. An old binary
that ignores a populated ledger could execute a used key again.

## Errors and transport integration

Add public `IdempotencyError` and one `ExecutionError::Idempotency(#[from]
IdempotencyError)` variant. Required cases and mappings are:

| Idempotency error | HTTP | Meaning |
|---|---:|---|
| `MissingKey` / `InvalidUuidV7` | 400 | opted-in input contract invalid |
| `Conflict` | 409 | tuple already bound to different canonical input |
| `InProgress` | 409 | another claimant owns the tuple; caller may retry |
| `Indeterminate` | 409 | prior claimed/failed attempt requires reconciliation |
| `StorageRequired` | 503 | no durable exact-replay store is configured |

Storage corruption/serialization/transaction errors remain `StorageFailed`
(500). E0000-11 must add the HTTP mapping and tower tests in the same wave as
its transport integration. `proof-transport-ws` also has an exhaustive match
and must be updated by the orchestrator: invalid input should use `-32602`,
conflict/in-progress/indeterminate a stable application conflict code, and
storage-required the existing internal/storage class. CLI and MCP currently
render unmatched errors generically and need behavior assertions but no
exhaustive-match repair.

## Required E0000-14 tests

Kernel unit tests:

- opted-out handlers retain legacy execution; opted-in missing, malformed, and
  non-v7 keys fail before handler entry;
- no/unsupported storage fails before handler entry;
- first call executes once and exact canonical retry returns equal output,
  proof ID, body, and signature; `execute` and both approval paths share it;
- same tuple with changed canonical input conflicts before handler entry;
- current approval/delegation checks occur before replay disclosure;
- concurrent claims enter a counting handler once, and a later retry replays;
- benchmark, handler, evidence, and completion failures never become completed
  records and same-key recovery never re-enters the handler;
- corrupted stored operation/input/output digest or claim token fails closed.

SQLite round-trip and migration tests:

- claim, completed replay, failed, in-progress, conflict, and exact idempotent
  completion round trips;
- completion atomically writes one context, one proof, canonical output, and
  proof JSON; induced validation/foreign-key failure rolls all of them back;
- two stores/connections racing on one file produce exactly one `Acquired`;
- reopen preserves a claimed row and never steals it;
- migration 11 is the next/fresh version, table constraints and primary key
  reject invalid rows, v10-to-v11 preserves existing data with an empty ledger,
  v11-to-v10 drops only the replay objects, reapply works, and concurrent
  openers apply v11 once.

Scoped E0000-14 commands are `rtk cargo fmt --check -p proof-kernel`, `rtk cargo
fmt --check -p proof-storage`, `rtk cargo test -p proof-kernel`, `rtk cargo test
-p proof-storage`, plus `rtk scripts/test-scoped.sh proof-kernel --list` for the
orchestrator's reverse-dependent impact set. E0000-06 then tests both opted-in
content handlers; E0000-10/11/12 test peer replay/conflict behavior and exact
proof identity. The orchestrator must include the WebSocket compile/error-map
