## SQL and lifecycle invariants

- Claims use `BEGIN IMMEDIATE`; the tuple primary key serializes same-key
  callers across SQLite connections. The first inserts `claimed`; later callers
  observe `InProgress`, `Conflict`, `Failed`, or the completed original outcome.
- File-backed and in-memory stores both enable `PRAGMA foreign_keys = ON` before
  migrations or replay work, so proof/context references have identical
  enforcement in production and tests.
- Application validation rejects a non-UUIDv7 idempotency key before insertion.
  `ContentDigest` supplies the validated 32-byte digest representation stored as
  64 hexadecimal characters.
- Completion verifies the persisted claimant/token/input plus proof operation,
  input digest, output digest, actor, delegation, and timestamp. It stores
  canonical output JSON and the original serialized proof.
- One immediate transaction inserts a new execution context, inserts the proof
  immutably, and transitions the ledger row to `completed` with both references.
  Exact completion retries are idempotent; differing completions conflict.
- Completed replay loading verifies canonical output, proof ID/envelope equality
  with immutable proof storage, and the referenced context's existence before
  returning the original `ExecutionOutcome`.
- Failure transition requires a nonempty failure, verifies the original
  claimant/token/input, and is exactly idempotent. A failed claim cannot complete.
- There is no claim expiry, lease, wait loop, stealing, deletion, automatic
  reopen, or retry path. Reopened `claimed` and `failed` records remain closed.

Replay tests cover acquired, in-progress, input conflict, exact completion and
replay, failed, wrong token, different completion, reopen, UUIDv7 validation,
foreign-key enablement/reference rejection, and persistence counts/envelopes.
An induced foreign-key failure occurs after
context/proof insertion but before the replay update and proves the whole
completion transaction rolls back to one untouched `claimed` row with zero
context/proof rows. Two stores/connections racing the same tuple produce one
`Acquired`, one `InProgress`, and one durable ledger row.

## Residual risks and rollback

- The approved residual crash window remains: a process can die after a domain
  mutation but before replay completion, leaving a durable `claimed` row. This
  implementation deliberately fails closed and requires operator/domain
  reconciliation followed by a new UUIDv7 key.
- Application and schema rollback is operationally unsafe while opted-in writers
  are active. Quiesce writers, preserve/export the ledger, revert replay policy
  so opted-in operations fail closed, then roll back to v10. An old binary that
  ignores a populated ledger could execute a used key again.
- Domain mutation and replay completion still cannot share one transaction under
  the frozen public handler boundary; E0000 does not redesign that boundary.
