# E0001-13 — Trusted fresh-workspace SQLite open

- Wave: W7
- Model/reasoning: `gpt-5.6-sol` / high
- Risk and owner gate: critical pre-key/database boundary; D-E0001-009 applies
- Dependencies: E0001-07, E0001-10, E0001-12

## Objective

Add one narrowly named storage API for opening an existing SQLite database in
an already validated, current-user-owned private directory. The API must use
stock SQLite's native no-follow protection, bind the ordinary pathname to
caller-owned directory/database descriptors before any migration or WAL
mutation, and retain those descriptors for the connection lifetime. It must
state and preserve D-E0001-009's fresh-workspace trust assumption; it must not
claim descriptor-pinned SQLite sidecar semantics.

## Required API and ordering

- Add a Linux-only seam such as
  `SqliteStore::open_existing_nofollow_in_trusted_directory(File, &Path, &str)`;
  unsupported targets fail closed with a specific error.
- Accept only an absolute ordinary expected directory path and one ordinary
  database-name component: reject slash, backslash, empty/dot/dot-dot, NUL,
  URI/query, traversal, or multicomponent input.
- Require the directory descriptor and pathname to identify the same directory
  by `(st_dev, st_ino)`, owned by the effective user, with no group/other
  permissions. Require the existing database opened relative to that
  descriptor with `O_RDWR|O_CLOEXEC|O_NOFOLLOW` to be a current-user-owned,
  single-link regular file.
- Before SQLite opens, reject any existing database `-wal`, `-shm`, or
  `-journal` leaf that is not a current-user-owned, single-link regular file;
  symbolic links always fail.
- Open the already existing ordinary database path with exactly read-write,
  no-mutex, and `SQLITE_OPEN_NOFOLLOW`; do not enable create or URI parsing.
- Before WAL, foreign-key, or migration initialization, verify the pathname
  still identifies the guarded database/directory and require
  `SQLITE_FCNTL_HAS_MOVED` to report false. Repeat those checks after
  initialization. Retain the directory and database guard descriptors until
  after the SQLite connection closes.
- Preserve existing `SqliteStore::open` and in-memory callers unchanged.

## Threat boundary and non-goals

This seam is defense in depth inside D-E0001-009's fresh private workspace. It
protects against malformed/static paths and unprivileged different-UID
substitution. Root and a hostile same-effective-UID process are explicitly out
of scope because stock SQLite cannot pin later WAL/SHM/journal pathname
operations without a descriptor-aware VFS, and such a process can already
access the private key and process credentials.

No custom VFS, mount/user namespace, database copy/hard-link staging, schema or
migration-content change, CLI/runtime/kernel/Content/contract edit, credential,
provider/live call, historical workspace, commit, push, or reverse-impact
suite.

## Acceptance

- A normal existing database opens, migrates, writes, reads, checkpoints WAL,
  closes, and reopens through the new seam.
- Database and existing sidecar symlinks/hard links are rejected with their
  targets unchanged. Missing databases are rejected rather than created.
- Wrong directory type/ownership/mode, directory fd/path identity mismatch,
  traversal/multicomponent/URI-like names, and unsupported targets fail before
  SQLite migration or mutation.
- Test hooks substitute the directory/database between descriptor validation
  and SQLite open, and between SQLite open and the pre-migration identity
  barrier; both fail with the replacement database schema/bytes unchanged.
- The API and errors never describe the connection or sidecars as
  descriptor-pinned, and the exact residual same-euid/root race is documented.
- Existing open/in-memory/migration tests remain green.
- `rtk cargo fmt --check -p proof-storage` passes.
- `rtk cargo test -p proof-storage --locked` passes.
- `rtk scripts/test-scoped.sh proof-storage` passes only after W7 quiesces
  under the orchestrator.

## Stop and escalate

Stop if the implementation needs a custom VFS, unsafe ownership relaxation,
creation of a missing database, URI handling, a schema/migration change, or a
cross-crate edit. Do not recreate E0001-12's impossible descriptor-pinning
claim and do not accept identity checks as protection against same-euid/root
namespace mutation.

## Handoff

Record API/flags, descriptor and drop lifetime, all identity/moved barriers,
sidecar checks, substitution/symlink/hard-link tests, commands/results, and the
exact residual threat assumption. Do not include workspace/database copies,
credentials, commits, or pushes.
