# E0001-09 — Credential-free live preparation

- Wave: W8
- Model/reasoning: `gpt-5.6-sol` / high
- Risk and owner gate: critical credential/evidence boundary; B5 remains inactive
- Dependencies: E0001-08, E0001-10, E0001-11, E0001-13

## Objective

Add a public, credential-free `agent live-prepare` workflow that creates the
fresh deterministic prerequisite evidence and safe synthetic edition material
required by the frozen live setup. It must exercise the real runtime,
approval, storage, evaluator, and setup-validation paths across a process
boundary without reading provider environment variables, constructing a live
gateway, sending a request, or creating the live provider-backed run.

## Writable paths (exclusive)

- `crates/proof-transport-cli/**`
- `editions/AXP-E0001/handoffs/E0001-09.md`

## Read-only references

- Approved E0001 contract, policy, decisions, and all accepted handoffs
- Kernel, storage, runtime, and Content public APIs
- Existing `agent live-start`, `agent live-resume`, approval, edition, and
  delegation CLI behavior

## Required workflow

1. Both phases require one caller-supplied, canonical UUIDv7 preparation ID.
   Before reading workspace config/key material or opening SQLite, the command
   validates D-E0001-009's fresh local trust boundary: a no-symlink ancestor
   walk protected against other-UID rename, current-euid-owned private root,
   `.proof`, and storage directories, then strict descriptor-relative,
   nofollow, regular, single-link config/key reads. It opens the already
   existing database only through E0001-13's native-no-follow trusted-directory
   seam. The descriptors remain live through the command. No ordinary
   `Workspace::open`, database creation, URI, or unverified pathname fallback
   is permitted, and the code must not claim SQLite sidecars are
   descriptor-pinned against a same-euid/root rename.
   Start safely creates a strict durable preparation record before dispatch and
   pre-binds every CLI-generated input identity, including edition,
   idempotency, deterministic agent, and an exact preparation-specific goal.
   Runtime-generated run/approval/evaluation IDs are recorded as soon as they
   exist. After a crash, recovery may adopt only the unique run/evaluation that
   exactly matches the saved agent, goal, trace, and preparation bindings;
   zero/duplicate/drifted candidates fail closed. Retries never select a
   latest run or generate replacement identifiers after output loss.
   A process-exclusive lock for that preparation ID is held across
   reconciliation, runtime start/resume, materialization, evaluation, and
   record publication so concurrent retries cannot duplicate the v1 effect.
2. `agent live-prepare start` uses the actual `AgentRuntime` with a
   deterministic scripted v1 gateway whose decision is statelessly derived
   from persisted `ModelInput`: Goal produces the exact v1 tool call and
   ToolOutput produces the terminal report. Normal runtime APIs persist the
   run, attempt, response, tool call, approval request, step, and events. The
   command stops at the real signed-approval boundary and emits only durable
   identifiers plus the exact next command as a JSON argv array.
   If the process dies inside runtime bootstrap, retry finds the unique exact
   saved run and delegates reconciliation only to E0001-11's public
   `AgentRuntime::resume`; CLI code never writes the missing ledger rows.
3. The existing approval CLI signs the exact persisted request in a separate
   process invocation.
4. `agent live-prepare finish` reopens SQLite, resumes that same run and
   approval-gated step through the actual runtime, seals the trace, evaluates
   it with `DeterministicTraceEvaluator`, and persists one immutable exact
   10/10 evaluation through the owning storage API. If interrupted after that
   append, retry finds the preparation-bound evaluation, recomputes it, and
   adopts it; it never appends a duplicate.
5. Finish safely materializes the preparation-bound synthetic edition input
   with descriptor-relative no-follow/create-new behavior, durable phase
   updates, and exact-byte/digest recovery. An unrelated existing target fails;
   an existing target may be reused only when the same preparation record binds
   it and no-follow reread proves exact equality. Finish derives the exact
   manifest digest, the already-bound UUIDv7 idempotency key, version label,
   and canonical live goal, then invokes only the existing live setup
   construction/validation in check-only mode.
6. Finish emits a strict point-in-time readiness packet containing the
   preflight run/evaluation IDs and evidence digest, frozen template/static
   digests, exact live AgentDefinition ID, and the nine non-run
   `LiveBindingInputs` needed by `agent live-start`. It must not invent a
   future live run ID, live trace/evaluation ID, 12-field resolved-binding
   digest, or resolved live-policy digest; those exist only inside the later
   provider-backed run. The digest-bound packet is durably persisted before it
   is printed so output loss is recoverable.
7. The check-only pass constructs the normal CLI `LiveRunSetup`, builds a
   credential-free runtime with a factory that must remain uninvoked, and calls
   E0001-10's authoritative runtime check API. CLI-only validation is not a
   substitute for runtime-owned target-agent/setup validation.

## Non-goals

No manual run/step/event/evaluation ledger fabrication, direct ad hoc SQLite
writes, runtime/Content/storage/kernel/contract edit, provider credential read,
provider construction or request, historical `.proof` reuse, external
deployment, paid attempt, live `AgentRun`, secret logging, commit, or push.

## Acceptance

- Start and finish are separate-process safe, resumable after interruption,
  and idempotent: rerunning a completed phase returns the same durable result
  without a second tool effect, artifact, terminal event, or evaluation.
- Lost stdout followed by retry with the same preparation ID returns the same
  run/approval/readiness packet; a different or malformed ID cannot adopt it.
- Concurrent start/finish retries serialize per preparation and cannot produce
  a second run, tool effect, edition, terminal event, or evaluation.
- The preflight journey is produced only through `AgentRuntime::start` and
  `AgentRuntime::resume`; the signed approval uses the existing public
  approval command and exact durable request.
- The deterministic result is sealed, independently recomputed, immutable, and
  exactly 10/10 with the frozen check IDs and stable trace/policy digests.
- The same sole enrolled Human who will be bound as live approver signs the
  deterministic request; the workspace Agent principal remains distinct.
- Synthetic edition creation rejects existing targets, symlinks, traversal,
  wrong identifiers, malformed manifests, non-UUIDv7 keys, and binding drift
  before any credential-capable boundary. No symlink-check/read or
  symlink-check/write TOCTOU window is accepted.
- Static symlink tests cover workspace root, `.proof`, config, keypair,
  storage, database, data, editions, and final edition leaves before any
  private-key read or database mutation.
- Fresh-workspace tests prove a root under root-owned sticky `/tmp` succeeds;
  wrong owner/mode, unsafe non-sticky writable ancestry, config/key/DB hard
  links, and injected initial directory/database substitution fail before
  key use, migration, or runtime mutation. The explicit same-euid/root residual
  threat from D-E0001-009 is documented, never presented as prevented.
- The final readiness check uses the same validation path as live start while
  factory, environment-read, constructor, and send spies all remain zero.
- Readiness creation leaves no provider-backed live run, `agent_runtime_v2`
  live checkpoint, live provider attempt, or preview artifact.
- Negative tests prove invalid approval, delegation, agent, edition, policy,
  evaluation, digest, or resume state cannot produce readiness.
- Integration tests use only fresh temporary workspaces, real SQLite, synthetic
  identities/data, and a deterministic in-process gateway; they use neither
  network nor provider environment credentials.
- At least one black-box test invokes start, existing approval, and finish as
  separate child processes. Interruption, concurrent retry, and symlinked
  workspace/data/edition component cases fail or recover without duplication.
- `rtk cargo fmt --check -p proof-transport-cli` passes.
- `rtk cargo test -p proof-transport-cli --locked` passes.
- `rtk scripts/test-scoped.sh proof-transport-cli` passes after the writer
  quiesces.

## Stop and escalate

Stop if this requires changing a shared/runtime/storage/Content contract,
weakening live-start validation, fabricating ledger state, touching a
historical workspace, or reading a provider credential. Return the exact
cross-owner request; B5 remains blocked.

## Handoff

Record command shapes, phase chronology, durable IDs/digests, runtime and
approval evidence, safe-filesystem checks, 10/10 independent recomputation,
zero credential/factory/send spy counts, commands/results, and residual risks.
Never include credentials, private key material, or a copied `.proof`
workspace/database.
