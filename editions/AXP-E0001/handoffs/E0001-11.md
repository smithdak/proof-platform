# E0001-11 Handoff — runtime bootstrap crash reconciliation

Result: owner-ready after independent-audit repair. Generic
`AgentRuntime::start` bootstrap is recoverable through public `resume` without
allocating a replacement run. The scoped runtime suite passes 110 tests.

## Changed files

- `crates/proof-agent-runtime/src/runtime.rs`
  - `start` and `resume` share runtime-owned generic bootstrap reconciliation.
  - Initial v1 state is derived from the durable run ID, bound agent, saved
    goal, and original run timestamp. The exact Started payload is constructed
    in one shared helper.
  - Queued revision 0 is the only state that may transition to Running during
    reconciliation. It uses the original durable creation timestamp, saves
    revision 1 once, and performs an exact run reread.
  - Checkpoint zero and Started event zero are separate exact barriers. Their
    UUIDv7 IDs, run IDs, sequences, payloads, canonical digests, and chronology
    are validated. Both stores are reread together before `drive` may run.
  - Existing exact barriers are reused. Duplicate initial checkpoints or
    Started events are never appended; every generic checkpoint/event envelope
    is contiguous, digest-valid, chronological, and v1-owned.
  - Approval events are never trusted by kind or count. Strict
    ApprovalRequired/ApprovalResumed data must preserve order and bind the
    exact ToolRequested call, step/request ID, operation/version/input digest,
    runtime-signed request, trusted-human signed decision/outcome, and any
    stored approval execution/proof. Only those verified transitions authorize
    exact step and run revisions. Waiting resumes pass the same evidence gate.
  - Run, checkpoint, and event timestamps in the future are rejected. Initial
    ordering remains agent creation <= run creation <= checkpoint zero <=
    Started zero.
  - Later generic checkpoints no longer imply safe progress. Before `drive`,
    runtime correlates immutable ModelRequested/ModelResponded lineage,
    response cursor, usage, cost, model-call counters, model ToolCall decisions,
    ToolRequested arguments, steps, pending state, and tool-attempt counters.
    An outstanding request or response/decision not durably materialized fails
    closed. The only event-free later checkpoint accepted is an exact
    pre-model terminal error carrying its persisted terminal-event intent.
  - Pending state binds the exact ToolRequested step, call ID, model tool name,
    operation, version, arguments, approval request, and input digest.
    ToolSucceeded/ToolFailed must be the next ordered result for that call and
    must bind the terminal step, signed proof or exact error, operation/version,
    and reconstructed `state.next_input`. A following model request is rejected
    until this result barrier is exact.
  - The recoverable post-tool split is deliberately narrow: when a terminal
    step and exact post-tool checkpoint were saved but the corresponding result
    event was not, runtime reconstructs the only permissible event from the
    original call plus signed proof/output or durable error. It appends once,
    rereads the unchanged event prefix plus exact suffix, and only then allows
    continuation. Conflicting evidence fails closed.
  - Resume resolves all immutable tool registry contracts before it may repair
    the Running row, initial checkpoint, or Started event. An unresolvable
    AgentDefinition leaves the partial run byte-for-byte untouched.
  - The pre-seal budget-recovery fixture now includes the real initial
    checkpoint before Started, matching the production ordering enforced by
    this task.
- `editions/AXP-E0001/handoffs/E0001-11.md`
  - This handoff only.

## Accepted partial states

1. Exact saved Queued run: Session mode, runtime actor, existing bound agent,
   nonempty goal, revision/retry `0/0`, equal creation/update timestamps, no
   completion, and no run-bound checkpoint/event/step/evaluation/approval
   evidence. Resume starts that same run once.
2. Exact saved Running run: revision/retry `1/0`, original start timestamp,
   and otherwise the same pristine evidence boundary. Resume writes only the
   exact initial checkpoint when absent.
3. Exact initial checkpoint without events: resume appends only Started event
   zero and rereads both barriers.
4. Exact checkpoint plus exact Started event: resume reuses both and continues
   only from later v1 state whose model, approval, step, tool-result, and
   checkpoint evidence is exactly correlated.

## Rejected states

- Wrong actor or bound agent, non-Session mode, empty/drifted goal/state,
  non-UUIDv7 run/agent, future agent definition, retry/revision/status or
  timestamp impossibility.
- Event evidence before checkpoint zero; non-Started event zero; bad/gapped or
  duplicate checkpoint/event envelopes; altered canonical digest; duplicate
  initial state or Started evidence; unknown checkpoint kind.
- Any step, evaluation, or request/step-bound approval execution while the
  bootstrap is incomplete. A lone initial checkpoint cannot coexist with
  later events, steps, evaluations, or approval evidence.
- Any partial shape that suggests later work. Recovery returns an error before
  gateway factory creation, model send, or tool execution and preserves the
  existing rows.
- Any extra checkpoint whose model-call counter lacks its exact
  ModelRequested/ModelResponded state-machine evidence, including an
  uncommitted request that could already have crossed the provider boundary.
- Forged or duplicated approval event pairs; request, step, input, signer,
  outcome, execution, or revision substitutions; and a pending call/tool that
  differs from ToolRequested or its durable step.
- Missing, reordered, or substituted ToolSucceeded/ToolFailed evidence,
  including step/call/operation/version/proof/error drift or a checkpoint
  `next_input` that cannot be reconstructed from the latest exact result.

## Fault and exact-once evidence

- One staged deterministic test interrupts the same durable run immediately
  after each successful save: Queued row, Running row, checkpoint zero, and
  Started event zero. Repeated public resume advances only the missing barrier;
  run count stays one and factory/model/tool spies stay `0/0/0` until both
  barriers reread exactly.
- Final resume completes that same run with exactly one initial checkpoint and
  one Started event. Terminal replay leaves all checkpoints/events unchanged
  and does not call the model again.
- A signed-approval recovery test interrupts after Started was saved but before
  its successful reread. Public resume pauses the same run, a trusted Human
  signs the existing request, the next process resumes and executes one tool
  effect, and repeated terminal replay keeps the effect count at one.
- The corruption matrix covers actor, agent/state, mode, goal, revision/time,
  checkpoint/event digest and duplication, non-Started/later events, orphan
  step, evaluation, and bound approval execution. Factory creation, model
  sends, and tool effects remain zero for every rejected case.
- Independent-audit regressions explicitly cover revision 2 at an otherwise
  exact boundary, revision-1 `updated_at` drift, future checkpoint and Started
  timestamps, an arbitrary `model_calls=1` checkpoint with no model event, and
  an unresolvable tool definition that must acquire no bootstrap evidence.
- A positive post-bootstrap fault after the durable ToolSucceeded event proves
  that fully correlated later generic state still delegates to normal resume,
  completes the same run, and keeps the tool effect exact-one.
- Deterministic pre-event faults cover the real checkpoint/result split for
  both ToolSucceeded and ToolFailed. Resume appends and rereads exactly one
  missing result event, sends the reconstructed success/failure output on the
  second model request, never replays the tool, and terminal replay is read-only.
- Adversarial redigested-read tests cover substituted checkpoint next input,
  pending call/tool/arguments, result step/call/operation/proof/error, step
  proof, and an internally consistent forged Required/Resumed request pair
  with substituted step/checkpoint bindings. Every case preserves underlying
  rows and records zero new gateway/tool work.

## Assumptions, residual risks, and cross-owner requests

- Approval executions have no independent run ID in the public API; runtime
  attributes them through the immutable approval-request-to-step binding and
  rejects every binding to this run during bootstrap. Completely unrelated
  approval rows for another run/actor are not treated as this run's evidence.
- Recovery does not infer model or tool work. Its only post-bootstrap write is
  the exact missing result event already proven by a terminal step and matching
  checkpoint; all other later recovery remains normal drive/approval/terminal
  behavior after the complete evidence gate.
- Reverse-impact testing is reserved for the orchestrator after W6 writers
  quiesce. Cross-owner requests: none.
- No credential/environment read, gateway construction, provider/network/live
  call, historical `.proof` workspace, schema/contract/migration edit, commit,
  push, or reverse-impact suite was used.
