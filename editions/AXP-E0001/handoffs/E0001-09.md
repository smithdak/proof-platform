## Public command shape

- `proof agent live-prepare start <canonical-uuidv7-preparation-id>`
- `proof agent live-prepare finish <same-id> --agent-id <live-agent-id> --delegation-id <delegation-id> --policy-file <frozen-policy>`

Start durably binds the preparation, synthetic edition, idempotency key,
deterministic v1 agent, exact goal, trusted Human approver, dispatch, runtime
run, approval step, and signed-request digest. It emits an exact JSON argv array
for the existing public approval command. Finish resumes that same run through
`AgentRuntime`, independently recomputes and appends/adopts one exact 10/10
trace evaluation, binds then safely publishes the synthetic edition, calls the
runtime-owned credential-free live setup checker, persists the readiness
record, and only then prints it.

The readiness packet contains the preflight run/evaluation/evidence and the
nine static live digests/non-run bindings. It deliberately does not claim a
future live run/evaluation/trace, resolved-policy digest, or 12-field resolved
binding digest.

## Security and recovery evidence

- Preparation IDs are explicit canonical UUIDv7 values; retries never select a
  latest run/evaluation or regenerate bound CLI identities.
- One OS/process-exclusive preparation lock spans reconciliation, runtime
  start/resume, evaluation, materialization, and readiness publication.
- The scripted gateway is stateless from persisted `ModelInput`: Goal maps to
  the exact v1 tool call and ToolOutput maps to the terminal report.
- Generic runtime bootstrap recovery now repairs exact partial
  Queued/Running, checkpoint-zero, and Started-event-zero barriers through
  public `AgentRuntime::resume`; CLI code performs no ledger repair.
- A real child-process kill after the bound run becomes durable and before
  `awaiting.json` publication recovers the same run and approval IDs with one
  AgentRun. Repeated start is identical.
- Completed start is a durable replay of the immutable initialized/awaiting
  chain. Completed finish is a durable replay of the immutable
  initialized/awaiting/evaluated/materialization/ready chain and caller-supplied
  agent/delegation/policy-path binding. Neither replay rechecks mutable
  approvers, registry, delegation, policy, runtime, or check-only state; the
  persisted `checked_at` remains the actual point-in-time validation.
- Replay tests remain exact after adding another approver, deleting the v2
  registry entry, expiring and revoking the delegation, and overwriting the
  policy path. Provider-boundary spies remain zero, while changed caller IDs or
  policy paths fail against the immutable packet.
- Preparation records are strict, digest-bound, immutable no-replace files.
  Digest verification is performed over the raw JSON, followed by typed decode
  and canonical raw-versus-typed equality so nested unknown/lossy fields fail.
- Synthetic edition publication uses a pinned directory descriptor, unnamed
  same-directory `O_TMPFILE`, synced open-fd publication, atomic no-replace
  `linkat`, directory sync, and exact no-follow reread. No writable pending
  alias remains.
- An unbound existing edition target fails even when byte-equal. A bound exact
  target is accepted only for recovery.
- Before config/key or SQLite consumption, live preparation descriptor-walks
  the absolute workspace ancestry without following components and rejects an
  ancestor not owned by root/current-euid, including a currently read-only
  other-UID-owned ancestor whose owner could later chmod it. Group/other
  writable ancestors are accepted only when sticky. A synthetic metadata test
  proves root-owned sticky `/tmp` semantics remain accepted. It retains handles
  for the current-euid-owned private root, `.proof`, and storage directories
  for the command lifetime.
- Config and keypair are read descriptor-relatively with no-follow, regular,
  current-euid owner, private mode, and single-link checks. The actor in config
  must equal the securely decoded key principal. Completed start/finish replay
  returns from its immutable phase chain without reopening key material or the
  database.
- Incomplete phases open the already-existing `storage.db` only through
  `SqliteStore::open_existing_nofollow_in_trusted_directory`, passing a cloned
  retained storage-directory descriptor and the verified absolute directory.
  There is no create, URI, ordinary `Workspace::open`, ordinary
  `SqliteStore::open`, or pathname fallback in live preparation.
- Child-process negatives cover workspace-root, `.proof`, config, keypair,
  storage, database, data, editions, and final-edition-leaf symlinks; config,
  keypair, and database hard links; nonprivate root/`.proof`/storage/config/key;
  and an unsafe non-sticky writable ancestor. Target key/database/edition bytes
  and relevant runtime counts remain unchanged.
- A real black-box start creates a fresh private workspace directly beneath
  root-owned sticky `/tmp`, asserts the production ancestor metadata, poisons
  both provider variables, and reaches the durable approval boundary without
  network or provider construction.
- Production does not invent registry contents. Exact active frozen v2 entry,
  schemas, and the Content handler/idempotency policy must already resolve;
  fresh tests explicitly provision the static registry fixture. The v2 entry
  is compared as raw canonical JSON before typed loading so unknown fields
  cannot disappear during deserialization; top-level entry and nested schema
  unknown-field regressions fail closed.
- The check-only path builds the normal `LiveRunSetup` and invokes
  `AgentRuntime::check_live_start_setup`. Factory, base-URL read, key read,
  constructor, and send spies are all exactly zero. No live v2 run/checkpoint,
  provider attempt, or preview artifact is produced.
- Deterministic evaluation verification recomputes the full trace result and

## Cross-owner dependencies and exact residual boundary

E0001-11 supplied the public crash-safe generic runtime reconciliation used by
start retry. E0001-13 supplied the public existing-database native-no-follow
trusted-directory seam. Both are consumed without a CLI ledger or storage
exception, so no unresolved cross-owner implementation request remains.

The accepted D-E0001-009 boundary intentionally does not defend against root or
a hostile same-effective-UID process. SQLite still uses ordinary pathnames for
the main database and sidecars after the storage seam's native no-follow,
identity, ownership/link, and moved-file barriers. The CLI therefore claims
neither descriptor-pinned SQLite sidecars nor safety from same-euid/root
namespace mutation. This is limited to a fresh disposable, current-user-owned
private workspace. No mock secure-store API or stronger claim is encoded.
