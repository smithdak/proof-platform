## API and open ordering

The new public Linux seam is:

```rust
SqliteStore::open_existing_nofollow_in_trusted_directory(
    directory: File,
    expected_directory: &Path,
    database_name: &str,
)
```

Non-Linux callers receive a specific `ErrorKind::Unsupported` storage error.
The Linux path executes these barriers in order:

1. Reject a non-absolute/non-ordinary expected directory and any database name
   containing an empty, dot, dot-dot/traversal, slash, backslash, NUL, control,
   URI, query, fragment, or multicomponent form.
2. Require the supplied directory descriptor and a native no-follow ordinary
   pathname guard to have equal `(st_dev, st_ino)`, be directories owned by
   the effective user, and grant no group/other permissions.
3. Open the existing database relative to the supplied directory. An `O_PATH |
   O_CLOEXEC | O_NOFOLLOW` type/owner/link preflight avoids opening a special
   leaf; the retained database guard then uses `O_RDWR | O_CLOEXEC |
   O_NOFOLLOW`. Both descriptors must identify the same current-user-owned,
   single-link regular file. No create flag occurs.
4. Before SQLite opens, inspect any existing `-wal`, `-shm`, and `-journal`
   leaf descriptor-relatively with no-follow and require a current-user-owned,
   single-link regular file. Missing sidecars are allowed.
5. Recheck directory/database pathname identities and sidecars immediately
   before SQLite open. SQLite receives only
   `SQLITE_OPEN_READ_WRITE | SQLITE_OPEN_NO_MUTEX | SQLITE_OPEN_NOFOLLOW`;
   create and URI flags are absent, and `sqlite3_db_readonly` must confirm the
   connection is actually read-write.
6. Before journal-mode, foreign-key, or migration work, require
   `SQLITE_FCNTL_HAS_MOVED == false`, then recheck directory/database identities
   and sidecars.
7. Initialize the unchanged WAL, foreign-key, and migration path. Repeat the
   moved-file, identity, ownership/type/link, and sidecar barriers afterward.

`SqliteStore` retains the supplied directory and opened database guards for the
connection lifetime. The connection field is declared before the guard field,
so Rust closes SQLite before dropping either guard and any SQLite close-time
filesystem work finishes first. Existing `open(Path)` and `in_memory()` keep
their prior flags and initialization behavior.

## Acceptance evidence

- An existing empty regular database migrates to v12, remains in WAL mode,
  writes and reads a principal, checkpoints WAL, closes, and reopens with the
  same data through the new seam.
- A missing database is rejected and remains absent. Unsafe database names,
  relative directory paths, a nondirectory descriptor/database leaf, a
  symbolic-link directory pathname, wrong private-directory mode, and
  descriptor/path identity mismatch all fail before migration or mutation.
- Database and existing WAL/journal sidecar symbolic links and hard links are
  rejected; their target bytes and the still-empty main database remain
  unchanged.
- Metadata validation tests exercise wrong effective-user ownership for both
  directory and database records without requiring privileged ownership
  mutation in the test process.
- The first test hook replaces either the directory pathname or database leaf
  after descriptor validation and before SQLite open. Both identity barriers
  fail with replacement bytes unchanged and the guarded empty database
  unmigrated.

  stock Unix VFS reports it moved through `SQLITE_FCNTL_HAS_MOVED`; the method
  fails before WAL/migrations, both the original and replacement lack the Proof
  migration table, and the replacement's marker schema/bytes remain unchanged.

## Exact residual boundary

This API is defense in depth only for D-E0001-009's fresh, current-user-owned
private workspace. SQLite continues to use ordinary pathnames for its main
database, WAL, SHM, journal, and deletion work. A hostile same-effective-user
process or root can still mutate that namespace after a barrier and is outside
the guarantee; either actor can already reach the workspace private key and
process credentials. The caller, E0001-09, must separately enforce the
no-symlink safe-ancestor walk and secure config/key reads before using this
seam. No custom VFS, namespace, path fallback, database creation, historical
workspace, credential, provider, network, live call, commit, push, or
reverse-impact run occurred.
